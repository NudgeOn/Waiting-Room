# 0006 — 유휴 대기열 유지보수의 읽기 경계

상태: 구현, 로컬 통합 검증 완료. 대규모 인원·최종 이미지 검증은 실행 기록을 따른다.

2026-09-10 06:18:37 UTC의 격리 Docker 인원 검사에서 `HOLD` 상태의 백그라운드
`promote`가 `deadline`, RPC 1,011ms, 남은 예산 999ms, 복구 mutex 대기 0ms를 기록했다.
설정은 유효했으며 이 쓰기 응답의 불확실성이 설치 공통 복구 fence를 올렸다. 해당 시간대
호스트 전원 로그에는 sleep/wake가 없었다. 디스크·VM 스케줄링·fsync 중 어느 지연이
최초 응답을 늦췄는지는 이 기록만으로 확정하지 않는다.

기존 `promote`는 승격·만료 정리가 필요 없는 경우에도 clock/dirty/commit을 기록했다.
새 `wr_queue_maintenance_v1`의 `wr_qm1_needed`는 동일 schema 5의 12개 키를
`FCALL_RO`로 검사한다. primary·epoch·fence·가용 상태·시계·설정을 확인하고, 각 만료
인덱스의 첫 항목만 조회한다. 다음 경우에만 기존 `wr_r6_command` 쓰기로 이어진다.

- 대기표·재시도 기록 또는 60초 rate 예약의 정리가 필요하다.
- AUTO/DRAINING에서 대기표가 있고 lease·rate 예산이 남아 있다.

읽기와 쓰기 사이에 변경이 생겨도 실제 쓰기가 기존 원자 함수에서 전부 다시 검사한다.
읽기 결과로 admission을 발급하거나 fence·TTL·quota를 바꾸지 않는다. 쓰지 않은 유휴
관측의 응답 유실은 다음 주기에 재관측하며 설치 전체를 불확실 쓰기로 만들지 않는다.
실제 승격 쓰기의 응답 유실, 잘못된 서버 상태·응답은 기존대로 차단한다. HOLD/OFF에서도
만료된 대기표와 재시도 기록을 계속 정리한다. RPC 제한·fsync·공개 quota는 유지한다.

기존 runtime v4/v5/v6 함수와 데이터 형식은 변경하지 않는다. 설치/업그레이드의 owner가
새 읽기 함수를 명시적으로 설치하고, serving Coordinator는 저장된 코드의 정확한 일치를
확인한다. 미설치·다른 코드일 때 자동 덮어쓰기나 구형 쓰기로의 조용한 우회는 하지 않는다.

검증은 직전 `fab5409` 소스 복사본과 같은 테스트를 비교했다. 구형 코드는 유휴 HOLD의
저장 상태를 변경했고 새 읽기 유실 경로가 없어 실패했다. 수정 후 12개 키의 DUMP 무변경,
읽기 응답 유실 후 기존 대기표·FIFO 유지, 실제 만료와 승격, 실제 쓰기 유실의 안전 대기를
검사했다. 이 결과는 지연을 유발한 호스트 하위 계층의 원인 규명이나 10K 지속 처리량
qualification을 대신하지 않는다.
