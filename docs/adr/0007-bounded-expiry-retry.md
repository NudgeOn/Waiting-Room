# 0007 — 확인된 만료 정리 이후 요청 재개

상태: 구현·전용 Valkey 회귀 검증. 실제 이미지 인원 수용 판정은 실행 기록을 따른다.

runtime v6는 한 번에 대기표 128개·재시도 기록 128개까지만 만료 정리한다. 더 남으면
`WR_SWEEP_REQUIRED`를 반환하며 요청 본체는 실행하지 않는다. 정리의 완료 응답과
cardinality commit은 유지된다. 기존 Go 호출자는 이를 공개 503으로 전달했다.
실제 재시도 기록 300개가 만료된 전용 Valkey에서 새 join이 실패하는 것을 재현했다.

v6 쓰기 호출은 이 확인된 응답에만 같은 인자로 최대 여덟 번 호출한다. 각 호출은 기존
epoch·primary·fence·시간·불확실 상태를 다시 검사하며 원래 context/deadline을 사용한다.
배치 크기, Lua 함수, 저장 형식, TTL, quota, fsync는 변경하지 않는다. 명시적 `Sweep`
호출은 기존 한 배치 계약을 유지한다. 구형 runtime 호출도 변경하지 않는다.

전송 장애·취소·알 수 없는 결과를 이 경로로 재시도하지 않는다. 정리 쓰기의 응답 자체가
유실되면 원래 `uncertain_write` 차단을 유지한다. 여덟 배치가 부족하면 기존 오류를
반환하므로 이 변경이 무한 대기나 모든 503의 제거를 의미하지 않는다.

회귀는 실제 300개 replay 만료의 RED/GREEN, 기존 방문자 301개와 정확한 FIFO/재시도,
1,024개를 초과한 잔여 정리의 상한, 실제 TCP 응답 유실 후 RECOVERY_HOLD,
정리 응답 직후 취소 시 다음 RPC 0회를 확인한다. 이전 인원 실행의 07:19:01 join 503은
최초 내부 오류가 기록되지 않아 이 재현과 동일한 원인이라고 단정하지 않는다.
