# 0008 — 복구 관측과 요청의 잠금 분리

상태: 구현·전용 Valkey RED/GREEN 검증. 실제 최종 이미지 수용은 실행 기록을 따른다.

1173fbf 이미지의 공개 인원 검사에서 632개 대기표를 보존한 채 join 쓰기가 deadline을
넘었다. 최초 진단은 recovery mutex 대기 1,103ms, RPC에 남은 예산 761ms,
실제 RPC 경과 811ms였다. MaintainRecovery는 INFO/FCALL 네트워크 호출 동안 이
mutex를 보유했고, 일반 요청이 마지막 승인 상태를 읽는 데도 같은 잠금을 사용했다.
별도 INFO 왕복도 1,362ms였으므로 잠금 제거만으로 환경의 모든 지연이 해결됐다고
판정하지 않는다.

복구 작업은 기존 mutex로 계속 직렬화한다. 서버 응답을 검증한 뒤 별개의 불변
RecoveryState 값을 atomic pointer로 공개하며 요청은 이 스냅샷을 즉시 읽는다.
초기 값이 없거나 로컬 불확실 상태 또는 공유 HOLD이면 기존 차단을 유지한다.
모든 실제 호출은 Valkey 안에서 primary·epoch·fence를 원자적으로 다시 검사한다.
오래된 ACTIVE 스냅샷으로 바뀐 공유 fence를 우회할 수 없다. 배포된 함수·저장 구조·
안전 대기·요청 deadline·쓰기 불확실성 처리에는 변화가 없다.

실제 Valkey 회귀에서 복구 잠금을 잡은 채 독립 join의 2초 예산을 검사한다.
수정 전에는 잠금을 풀 때까지 요청이 끝나지 않았고 수정 후에는 정상 완료했다.
불변 값 보존, 현재 HOLD의 RPC 0회, 강제로 오래된 ACTIVE 값을 읽었을 때의 서버
차단·전체 저장값 보존, 첫 검사 직후 취소, 실제 쓰기 응답 유실의 recovery hold를
함께 확인한다. 이 변경은 네트워크/fsync 지연을 무시하거나 실패 쓰기를 재시도하지 않는다.
