# 0009 — 동일 설정 확인의 쓰기 잠금 제거

상태: 구현·RED/GREEN 회귀 검증. M2의 실제 최종 이미지 판정은 실행 기록을 따른다.

Node는 매초 서명 설정을 확인한다. 기존 apply는 동일 generation인지 확인하기 전에
전체 Node의 RWMutex 쓰기 잠금을 요청했다. 공개 요청·큐 유지보수는 네트워크 I/O가
끝날 때까지 읽기 잠금을 보유한다. 따라서 같은 설정을 확인하는 작업도 기존 요청을
기다렸고, 대기 중인 writer가 뒤따르는 새 reader까지 막았다. 네트워크 지연이 전체
요청 대기로 확대되며 Gateway의 3초 제한과 Coordinator의 2초 예산이 어긋날 수 있었다.

유효한 payload를 검증한 다음 읽기 잠금으로 현재 generation을 확인한다. 같으면
쓰기 잠금 없이 끝낸다. 새 generation은 기존 쓰기 잠금과 내부 재확인을 유지한다.
실제 설정 교체·기존 handler/store 수명·서명 gate·fence·RPC 제한·Valkey 내구성은
바뀌지 않는다. 변경되지 않은 generation을 확인하는 데 필요 없던 배타 대기만 없앤다.

회귀는 진행 중인 요청을 모의하는 읽기 잠금을 잡은 채 같은 설정을 확인한다. 기존
코드는 300ms 안에 끝나지 않았고 수정 후 즉시 완료했다. 잘못된 payload의 거부와
실제 새 설정의 요청 종료 대기를 함께 10회 race 모드로 검사했다.

이 증거는 잠금 증폭 경로를 확인한다. 단독 Docker 인원 검사에서 관측한 Valkey INFO
1.9초 지연의 근본 원인까지 확정하거나 모든 503이 해결됐다는 뜻은 아니다.
