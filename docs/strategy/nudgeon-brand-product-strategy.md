# NudgeOn Brand & Product Strategy

작성일: 2026-09-06 · 전략 제안 v1.0 · 대상: 브랜드, 제품, 개발, 초기 사업 운영

**NudgeOn은 한국 서비스 팀을 위한 고객 행동 기반 멀티채널 메시징 제품을 중심으로, NudgeOn Waiting Room을 독립 제품군으로 확장한다. 두 제품이 공유하는 약속은 ‘위자드로 쉽게 시작하고, 우리 인프라에서 직접 운영한다’이다.**

사업화 순서는 **오픈소스·직접 설치 → 유료 운영 지원 → 관리형 SaaS**로 둔다. 브랜드와 설치 경험의 원칙은 공유하고, 각 제품의 구매 가치·설치·배포·출시 판단은 독립적으로 관리한다.

## 1. 이번 전략의 기준

| 구분 | 기준 |
|---|---|
| 사용자 정의 | NudgeOn은 한국형 Braze를 지향하는 고객 행동 기반 멀티채널 메시징 제품 |
| 사용자와 합의한 제품군 | NudgeOn Waiting Room을 같은 브랜드 아래 별도 제품으로 추가 |
| 사용자가 강조한 공통 장점 | 두 제품 모두 위자드를 통해 아주 쉽게 설치하는 경험 |
| 사용자가 선택한 사업화 순서 | 오픈소스·직접 설치, 유료 지원, 관리형 SaaS 순서 |
| 이 문서의 제안 | 고객 우선순위, 브랜드 문구, 사이트 구조, 상품 구성, 측정 지표와 90일 검증 계획 |

이 문서는 제품 전략과 시장 검증 계획이다. 기존 제품 PRD의 기술 범위나 출시 gate를 변경하지 않는다. 제안한 이름·URL·요금 구성·일정이 실제 서비스에 적용되었다는 의미도 아니다.

## 2. 경쟁 환경에서 선택할 위치

Braze는 행동에 따른 여정과 채널 간 메시징을 설명하며, 현재 KakaoTalk도 별도 제품 페이지에서 안내한다. 따라서 ‘Braze에는 한국 채널이 없다’를 차별화 근거로 사용하지 않는다. [Braze Journey Orchestration](https://www.braze.com/product/journey-orchestration), [Braze KakaoTalk](https://www.braze.com/product/kakaotalk-messenger)

국내 핵클도 행동 데이터, 세그먼트, 자동화 메시징과 카카오 채널을 제공한다고 설명한다. Dittofeed는 오픈소스·셀프호스팅·멀티채널 메시징을 내세운다. ‘한국형’, ‘오픈소스’, ‘멀티채널’ 각각만으로 독점적 차별화를 주장하기는 어렵다. [핵클 CRM](https://www.hackle.io/ko/service/crm-marketing/), [Dittofeed](https://www.dittofeed.com/)

Waiting Room의 경쟁 범주는 웹·앱의 유입과 입장 속도를 제어하는 제품이다. Queue-it도 사이트 병목 구간, 웹·네이티브 앱 적용, 운영 대시보드를 설명한다. 메시징과는 고객이 구매하는 이유와 평가 기준이 다르다. [Queue-it Traffic Control](https://queue-it.com/traffic-control-insights/)

이에 따른 **전략 가설**은 다음 조합이다.

> 한국 팀의 실제 운영 흐름에 맞는 제품 + 위자드로 첫 성공까지 이어지는 설치 + 직접 운영하는 선택권 + 문제를 해결해 주는 한국어 지원.

쉬운 설치는 첫 도입의 장벽을 낮춘다. 장기 경쟁력은 설치 실패 사례를 제품에 반영하는 속도, 채널·운영 연동의 완성도, 업그레이드와 복구 경험, 반복 도입 사례로 쌓는다. 경쟁 제품보다 빠르거나 저렴하다는 주장은 비교 측정 후에 사용한다.

## 3. 브랜드 구조와 이름

| 계층 | 이름 | 고객에게 설명할 내용 |
|---|---|---|
| 공통 브랜드 | **NudgeOn** | 쉽게 시작하고 직접 운영할 수 있는 제품을 만든다는 신뢰 |
| 대표 제품 | **NudgeOn** | 한국 팀을 위한 고객 행동 기반 멀티채널 메시징 |
| 인접 제품 | **NudgeOn Waiting Room** | 웹·앱 트래픽 대기열과 입장 제어 |
| 도입 방식 | 직접 설치 / 유료 지원 / 향후 관리형 | 같은 제품을 누가 설치·운영하고 지원하는지 |

대표 제품의 이름은 지금처럼 NudgeOn으로 유지한다. 메뉴·비교표·견적에서는 **‘NudgeOn — 고객 행동 메시징’**과 **‘NudgeOn Waiting Room — 트래픽 대기열’**로 구분한다. `NudgeOn Engage` 같은 추가 제품명은 고객의 선택·견적 과정에서 혼동이 반복될 때 검토한다.

두 제품은 각각 단독 설치·구매가 가능해야 한다. Waiting Room 도입에 메시징 설치를 요구하지 않는다. 관리형 서비스도 별도 제품 이름을 계속 늘리기보다 각 제품의 도입 방식으로 설명한다.

### 공통 브랜드 원칙

- **쉽게 시작:** 필요한 결정을 위자드가 안내하고, 첫 사용 결과를 확인하게 한다.
- **직접 운영:** 고객이 자신의 인프라와 운영 정책을 선택한다.
- **상태를 이해:** 진행 상황, 실패 이유, 다음 행동을 사람이 이해할 수 있게 설명한다.
- **한국 팀에 적합:** 한국어 운영 UX·문서·지원과 국내 메시징 업무 흐름을 제품에 반영한다. 지원 채널은 실제 검증 범위로 표시한다.

로고·서체·기본 색·버튼과 폼·상태 표현·위자드 패턴은 공유한다. 제품마다 로고를 새로 만들기보다 NudgeOn 로고에 제품 이름을 함께 표시한다. Waiting Room의 방문자용 대기 화면에서는 도입 고객의 브랜드와 안내가 우선 보이도록 한다.

## 4. 바로 사용할 메시지 체계

아래 문구는 브랜드·제품 방향의 제안이다. 공개 페이지에서 설치 완료나 제공 기능을 표현할 때는 해당 버전의 검증 상태를 함께 표시한다.

| 용도 | 제안 문구 |
|---|---|
| 공통 브랜드 슬로건 | **쉽게 시작하고, 직접 운영하세요.** |
| 공통 설명 | 위자드로 설치하는 오픈소스 제품. 고객 메시징과 트래픽 대기열을 우리 인프라에서 운영하세요. |
| NudgeOn 제목 | **고객의 행동을, 다음 메시지로.** |
| NudgeOn 설명 | 한국 팀을 위한 고객 행동 기반 멀티채널 메시징. 이벤트, 세그먼트, 여정을 연결하고 필요한 채널로 소통하세요. |
| NudgeOn 설치 메시지 | 위자드를 따라 설치하고, 첫 테스트 메시지부터 확인하세요. |
| Waiting Room 제목 | **고객이 몰리는 순간에도, 입장은 차례대로.** |
| Waiting Room 설명 | 웹과 앱의 유입을 대기열로 받아 입장 속도를 조절하세요. 위자드로 설치하고 운영 화면에서 제어합니다. |
| 설치 CTA | 설치 시작하기 / 설치 과정 보기 |
| 검증 단계의 CTA | 설치 미리보기 / 파일럿 문의 |
| 지원 CTA | 운영 지원 상담 |

‘한국형 Braze’는 제품 범주를 빠르게 설명하는 비교 표현으로 사용한다. 주된 공개 소개는 NudgeOn 자체의 고객·문제·해결 방식을 설명한다. 설치 시간을 측정하기 전에는 ‘누구나 5분’, ‘개발 지식 없이 모든 환경에 설치’, ‘완전 자동 운영’ 같은 표현을 사용하지 않는다.

## 5. 제품별 고객과 우선 해결할 문제

| 항목 | NudgeOn | NudgeOn Waiting Room |
|---|---|---|
| 초기 고객 가설 | 작은 개발팀과 CRM·그로스 담당자가 있는 한국 B2C 앱·커머스·구독 서비스 | 설치를 맡을 개발자가 있는 웹·앱 서비스 및 행사 운영팀 |
| 도입 주도자 | 개발 리드·CTO + CRM·마케팅 담당자 | 개발 리드 + 서비스·행사 운영자 |
| 구매 계기 | 고객 행동별 메시지가 개별 개발과 수작업으로 분산됨 | 오픈·판매·신청 일정에 접속이 몰림 |
| 핵심 가치 | 행동·세그먼트·여정·채널을 연결해 반복 메시징을 운영 | 정해진 입장 속도와 순서로 원본 서비스의 유입을 제어 |
| 첫 체험 | 샘플 이벤트와 Test Inbox에서 메시지 흐름 확인 | 테스트 사이트에서 대기·입장·복귀 확인 |
| 실제 도입 증거 | 고객 이벤트에서 선택한 실제 채널의 결과까지 추적 | 실제 연동 환경에서 설정 반영·입장·장애 시 동작 확인 |
| 초기 활용 예시 | 가입 후 첫 행동 안내, 관심 행동 후 후속 안내, 재방문 여정 | 한정 판매, 회원 신청, 콘텐츠 공개 전 사전 리허설 |

첫 고객은 제품을 직접 운영할 의사가 있고 설치 담당자가 있는 팀으로 좁힌다. 마케터가 서버를 관리할 필요 없이, 개발자가 위자드로 설치하고 운영 담당자가 제품 화면을 사용하는 역할 분담을 만든다.

두 제품의 교집합인 커머스·반복 이벤트 서비스는 함께 검증하되, 두 제품을 동시에 필요로 하는 고객만 찾지는 않는다. 각각의 제품으로 첫 성공과 유료 지원 가치를 만들어야 한다.

NudgeOn은 한국형 멀티채널이라는 방향을 유지하며, 우선 검증한 한 채널과 한 여정을 끝까지 완성한다. Waiting Room은 설치·운영 제어·복구와 검증된 처리 범위를 우선한다. 새로운 기능의 개수보다 실제 설치와 반복 운영의 막힘을 먼저 줄인다.

## 6. 설치 위자드를 제품군의 핵심 자산으로

위자드는 두 제품을 같은 브랜드로 묶는 가장 직접적인 경험이다. 단순한 설정 입력 화면을 넘어 **설치 → 첫 체험 → 실제 연결 → 운영 준비**가 이어지도록 한다.

| 공통 단계 | NudgeOn | NudgeOn Waiting Room |
|---|---|---|
| 준비 점검 | 호스트·저장소·필수 서비스 상태와 해결 안내 | 호스트·저장소·연동 방식과 필요한 환경 점검 |
| 안전한 기본 설정 | 설치 소유권, 최초 관리자, 권장 설정 | 최초 관리자, 보안 설정, 기본 Room 안내 |
| 외부 의존 없는 체험 | 샘플 이벤트 → Test Inbox 수신 | 샘플 사이트 → 대기 → 입장 → 복귀 |
| 고객 환경 연결 | 실제 이벤트·선택한 채널 하나 연결 | 실제 웹사이트·앱과 경로·입장 설정 연결 |
| 결과 확인 | 접수·공급자 수락·수신을 구분해 확인 | 설정 저장·runtime 반영·실제 입장을 구분해 확인 |
| 다음 운영 안내 | 상태 확인·다음 여정·업그레이드 안내 | 상태 확인·리허설·안전 종료 안내 |

공통 UX 기준은 권장 기본값, 단계별 필요한 입력, 중단 후 이어하기, 실패 원인과 재시도 안내, 완료 결과 확인이다. 제품별 위자드의 화면 원칙과 문구는 공유하고, 설치 엔진이나 데이터베이스를 억지로 하나로 합치지는 않는다.

호스트 준비·DNS·외부 발송 계정 승인은 제품 설치와 따로 안내한다. 표준 환경에서 쉽게 설치할 수 있다는 장점을 유지하면서, 고객이 준비해야 하는 항목도 시작 전에 알 수 있게 한다.

### 설치 성과의 측정

| 지표 | 측정 방식 |
|---|---|
| 안내 없이 설치 완료한 비율 | 사전 조건을 충족한 새 설치 중 담당자 개입 없이 안전한 관리자 설정까지 완료한 비율 |
| 첫 체험까지 걸린 시간 | 위자드 시작부터 Test Inbox 수신 또는 실제 테스트 대기·입장까지 |
| 고객 환경 연결까지 걸린 시간 | 실제 이벤트·채널 또는 실제 사이트 연결 시작부터 검증 완료까지 |
| 막힌 단계 | 시작한 모든 설치의 중단·실패·지원 요청 위치와 이유 |
| 재개 성공 | 중단·재시작 후 기존 진행 상태에서 이어서 완료했는지 |
| 지원 부담 | 설치당 사람의 지원 시간, 같은 문제의 반복 발생 횟수 |

설치 시간은 호스트 사양·제품 버전·다운로드 포함 여부와 함께 기록한다. Test Inbox와 실기기 도달, 대기열 설정 저장과 실제 입장을 같은 완료 지표로 합치지 않는다. 기존 [NudgeOn 위자드 PRD](/Users/youngjoo/ethan/onda/onda-platform/docs-public/DOCKER-SETUP-WIZARD-PRD.md)의 단계별 지표 정의를 따른다.

초기에는 **제품별 외부 사용자 5명의 관찰 설치와 지원 없이 첫 체험을 끝낸 4명 이상**을 학습 목표로 제안한다. 이는 신규 제안이며 현재 실적이나 출시 gate가 아니다. 표본이 작으므로 4/5를 전체 시장의 80% 성공률로 일반화하지 않는다. 설치 기록은 로컬 또는 참여자가 동의한 파일럿에서 수집한다.

## 7. 수익모델: 쉬운 설치에서 운영 신뢰로

| 단계 | 고객이 얻는 것 | 요금 구조 가설 |
|---|---|---|
| 오픈소스·직접 설치 | 제품 코어, 위자드, 문서, 기본 진단과 커뮤니티 이용 | 소프트웨어 무료, 고객의 인프라·외부 발송 비용 별도 |
| 도입 지원 | 기존 시스템 연결, 특수 환경 설정, 이전과 운영 교육 | 합의한 작업 범위의 일회성 지원료 |
| 운영 지원 | 업그레이드 계획, 복구 점검, 문제 진단, 정해진 시간의 대응 | 지원 범위·시간·환경 수에 따른 정기 계약 |
| Waiting Room 행사 지원 | 행사 전 설정 검토, 부하·복구 리허설, 합의한 일정의 지원 | 행사·준비 범위별 패키지 실험 |
| 향후 관리형 SaaS | 설치·호스팅·업데이트·운영을 맡기는 서비스 | 제품별 기본 운영료와 비용을 설명할 수 있는 사용량 기준 검토 |

**무료 위자드만으로 표준 설치를 완료할 수 있어야 한다.** 유료 지원의 가치는 특수 환경과 운영 부담을 해결하는 데 둔다. 기본 설치를 어렵게 만들거나 안전한 기본 기능을 잠가 유료 지원으로 유도하지 않는다. 이는 기존 [NudgeOn 비전 PRD](/Users/youngjoo/ethan/onda/onda-platform/docs/prd/PRD-00-비전-전략.md)의 전체 공개·운영 수익화 방향과도 맞는다.

초기 가격은 고객의 지불 의사와 실제 지원 원가를 확인한 뒤 정한다. 견적에는 지원 범위·담당 시간·외부 비용·완료 조건을 명시한다. 메시징의 공급자 발송료와 Waiting Room의 인프라 비용은 지원료와 구분한다.

가격 검증에서는 도입 작업 한 건의 소요 시간·직접 비용·재작업 시간과 계약별 반복 지원 시간을 기록한다. 고객이 요청하는 서비스 중 반복적으로 제공 가능하고 지원 원가를 감당할 수 있는 범위를 정기 상품으로 만든다. 무제한 지원이나 상시 대응은 인력·운영 체계가 뒷받침될 때만 제공한다.

관리형으로 넘어갈 때도 두 제품이 같은 날 출시될 필요는 없다. 반복 운영 절차, 업그레이드·복구, 고객 수요와 직접 운영 원가가 확인된 제품부터 검토한다. Waiting Room의 SaaS는 현행 v1 제외 범위 이후 별도 제품 계획이다.

메인 메뉴는 **제품 / 설치하기 / 문서 / 운영 지원 / GitHub**로 단순하게 구성한다. 제품 메뉴에서는 **고객 행동 메시징 / Waiting Room**을 명확히 구분한다. 상위 브랜드의 넓은 문구가 NudgeOn의 메시징 카테고리를 가리지 않게 한다.

각 제품 소개 페이지의 순서는 **해결하는 문제 → 실제 사용 화면 → 위자드 설치 과정 → 현재 제공 범위 → 직접 설치와 지원 선택**으로 둔다. 주요 시연 자료는 빈 환경에서 첫 체험까지 이어지는 영상과 화면이다. 시간 수치는 측정한 조건을 함께 표시한다.

새 도메인 구매는 보류한다. 기존 도메인의 경로를 우선 사용하고 필요한 경우 서브도메인을 연결한다. 서브도메인은 기존 도메인에 DNS 레코드를 추가하는 방식이며 별도 도메인 등록·갱신이 필요하지 않다. 호스팅과 실제 운영 비용은 따로 발생할 수 있다. [Cloudflare 서브도메인 안내](https://developers.cloudflare.com/dns/manage-dns-records/how-to/create-subdomain/)

직접 설치형 고객의 제품은 고객 인프라·주소에서 실행된다. `waiting.nudgeon.io`를 확보하는 것과 고객의 대기열을 대신 운영하는 SaaS는 다른 작업이다.

## 9. 초기 유입과 판매 동선

제품별 기본 동선은 **문제 검색·개발자 콘텐츠 → 실제 설치 시연 → 오픈소스 설치 → 첫 체험 → 고객 환경 연결 → 필요에 따른 지원 상담**이다.

| 제품 | 첫 콘텐츠·시연 | 첫 제안 |
|---|---|---|
| NudgeOn | 위자드 설치 후 이벤트 하나로 테스트 메시지까지 연결하는 과정 | 한 개의 실제 고객 여정을 함께 검증하는 파일럿 |
| Waiting Room | 테스트 사이트에서 입장 속도를 바꾸며 대기·입장을 확인하는 과정 | 다음 오픈 일정 전 제한된 환경에서 설치·리허설하는 파일럿 |

개발자가 설치하고 내부 운영 담당자에게 전달할 수 있도록 설치 가이드와 운영 시작 가이드를 구분한다. 마케터에게는 실제 여정 구성과 결과 확인을, 이벤트 운영자에게는 입장 설정과 상황 판단을 보여준다.

초기 디자인 파트너는 각 제품을 직접 사용할 담당자가 있는 팀을 대상으로 모집한다. 설치와 사용 관찰에서 나온 반복 문제를 제품에 반영하고, 고객이 동의한 사례만 공개한다. 다운로드·GitHub 별 수와 함께 실제 설치·반복 운영·지원 구매를 본다.

공동 활용 사례는 한정 판매·회원 신청처럼 사전 안내와 접속 집중이 이어지는 상황에서 검증한다. 각 제품의 단독 도입 경로를 유지하고, 다른 제품 추천은 고객의 실제 문제에 맞을 때 한다.

## 10. 제품 간 연동과 관리 경계

지금 공유할 것은 브랜드 자산, 홈페이지, 문서 탐색, 위자드 UX 원칙, 지원 접수 방식과 공통 개발 관례다. 저장소·릴리스·설치·runtime·운영 데이터·장애 대응 범위는 제품별로 유지한다.

연동은 각 제품의 단독 사용이 검증된 뒤 **Waiting Room 이벤트 → 선택형 비동기 연동 → NudgeOn 여정**으로 검토한다. 메시징이 지연되거나 멈춰도 대기 순서·입장·원본 보호는 독립적으로 동작해야 한다.

‘입장 가능 알림’은 가능한 후속 활용 사례이지만 채널 지연과 입장 유효시간을 함께 설계해야 한다. 이미 만료된 입장을 뒤늦게 안내하지 않도록 하고, 메시지 수신 자체가 입장 권한을 부여하지 않게 한다. 고객 식별과 수신 설정의 연결도 선택 연동 범위에서 명확히 한다.

연동 고객이 생기기 전에 공통 로그인·결제·고객 데이터베이스·필수 통합 SDK부터 구축하지 않는다. 제품별 설치 성공과 반복 운영 개선에 개발 시간을 먼저 사용한다.

## 11. 90일 실행·검증 계획

아래 일정과 수치는 **제안 목표**다. 현재 성과나 출시 약속이 아니며 각 제품의 기존 기술·운영 gate가 우선한다.

| 기간 | 실행할 일 | 다음 단계의 판단 근거 |

| 1–30일 | 제품명·설명·지원표 정리, 공통 위자드 기준 수립, 제품별 고객 인터뷰 5곳과 새 환경 설치 관찰 시작 | 고객이 두 제품을 구분하고, 설치의 실제 막힘과 필요한 첫 사용 사례를 확인 |
| 31–60일 | 제품별 관찰 설치 5건 완료 목표, 반복 실패 개선, 제품별 실제 환경 파일럿 2곳 목표 | 표준 설치·첫 체험과 실제 고객 환경 연결을 구분해 증명하고 제품별 기술 gate 검토 |

NudgeOn은 행동→여정→선택한 실제 채널의 결과와 운영 신뢰성을 우선 검증한다. Waiting Room은 현재 Beta 계획의 runtime·운영 UI·설치·복구 검증을 우선한다. 전략 문서 때문에 진행 중인 제품 개발의 기술 순서를 임의로 바꾸지 않는다.

매월 공통으로 볼 지표는 **지원 없이 첫 체험을 완료한 설치 수, 고객 환경에서 반복 사용하는 설치 수, 설치·지원 소요 시간, 유료 지원 전환과 직접 원가**다. 제품 성과는 NudgeOn의 유효 여정과 채널 결과, Waiting Room의 설정 준수와 원본 보호·복구 결과로 나누어 본다. 서로 다른 단위의 지표를 하나의 제품군 성공률로 합치지 않는다.

## 12. 현재 문서와의 정합성 및 후속 반영

이번에 읽은 로컬 문서 기준으로 NudgeOn은 alpha/Safe Boot Preview를 명시하며, README에는 푸시 중심 소개와 이메일 구현 설명이 함께 있다. Waiting Room은 로컬 Control·대기열 구현과 별개로 Beta 및 production qualification이 미완료라고 명시한다. 이번 작업은 문서 검토이며 전체 코드·실기기·신규 호스트 설치 재검증은 수행하지 않았다. [NudgeOn README](/Users/youngjoo/ethan/onda/onda-platform/README.md), [NudgeOn 위자드 PRD](/Users/youngjoo/ethan/onda/onda-platform/docs-public/DOCKER-SETUP-WIZARD-PRD.md), [Waiting Room README](../../README.md), [Waiting Room Beta 계획](../beta-plan.md)

따라서 **‘위자드로 아주 쉽게 설치’는 두 제품의 핵심 브랜드·제품 전략으로 채택**하고, 실제 공개 문구의 완료 표현과 소요 시간은 해당 버전의 관찰 설치 결과로 뒷받침한다. NudgeOn은 제품 비전을 푸시로 축소하지 않으며, 채널별 구현·통합 검증·일반 제공 상태를 별도 지원표로 정리한다. Waiting Room의 10K/100K는 현행 PRD의 qualification profile로 유지하고 검증된 동시 접속 성능이나 요금 등급으로 바꾸지 않는다. [Waiting Room Main PRD](../main-prd.md)

후속 반영 순서는 다음과 같다.

1. NudgeOn 기존 비전 문서의 초기 사업화 순서를 사용자 결정인 **직접 설치 → 유료 지원 → 관리형**으로 정렬한다.
2. 제품별 지원 상태표와 설치 완료 기준을 정리하고, 오래된 경쟁사 단정과 공개 소개의 혼재를 수정한다.
3. NudgeOn 사이트에 제품 메뉴와 Waiting Room 소개·문서 진입점을 추가한다.
4. 두 제품의 위자드와 관찰 설치 결과를 공통 형식으로 공개한다.
5. 실제 지원 수요·제공 범위·원가를 확인한 뒤 지원 상품을 안내한다.

이 전략 문서 작성 범위에서는 위 사이트·제품·PRD 변경이나 외부 게시를 실행하지 않았다.
